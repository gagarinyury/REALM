# Импорт DROID из URDF — штатный путь вместо ремонта бинарного ассета

> **ИТОГ 10.08.2026: собранный этим рецептом робот `droid2` НЕ ГОДИТСЯ, и работа переведена
> на стоковый `franka_robotiq` (`realm/config/robots/DROID_franka_robotiq.yaml`).**
> Причина — в разделе «Почему сборка отклонена» в конце файла. Рецепт оставлен, потому что
> сам по себе он верен и в нём разобраны семь отдельных граблей; негодной сборку делают
> исходные данные — геометрия гриппера, которой в репозитории REALM нет.

Сделано 10.08.2026. Заменяет собой три скрипта ремонта (`untangle_droid_gripper.py`,
`align_droid_root.py`, `lift_gripper_velocity_clamp.py`) и всю конструкцию на mimic-связях.

## Почему

Документация OmniGibson (`docs/tutorials/custom_robot_import.md`, таблица чистильщиков URDF)
предписывает прямо противоположное тому, что делает наш ремонт ассета:

> `strip_mimic_joints(tree)` — удаляет все `<mimic>`. Импортёр **не создаёт привод** на
> mimic-суставе, из-за чего ведомый палец остаётся неприводным.
> **Пусть оба пальца ведёт контроллер во время работы.**

Наш ремонт строил гриппер именно на mimic-связях, и наблюдалось ровно то, о чём
предупреждает документация: ведомые суставы не дотягивают за ведущими (0.55 против 0.785),
пружинят, расходятся в противофазе, губки встают под углом ~90° друг к другу.

Проверено отдельно: вернуть авторскую схему (замкнутый параллелограмм + гриппер вне
артикуляции через `physics:excludeFromArticulation`) на OmniGibson 3.9.1 **невозможно** —
после отключения всех пяти мешающих проверок движка процесс падает в нативном коде
(`Segmentation fault`, без единого Python-кадра). То есть разрыв петли на новой версии
неизбежен, вопрос только в том, чем заменить механическую связь.

## Рецепт

```bash
# 1. Очистить URDF: убрать mimic-связи
python - <<'PY'
import xml.etree.ElementTree as ET
from omnigibson.utils.urdf_preprocessing import strip_mimic_joints, urdf_audit
t = ET.parse('realm/robots/panda_robotiq/panda_robotiq_85.urdf')
strip_mimic_joints(t)                      # -> 5 связей удалено, пальцы становятся приводными
t.write('panda_robotiq_85_clean.urdf', encoding='utf-8', xml_declaration=True)
PY

# 2. Достать геометрию гриппера (в репозитории её нет — только описание)
#    Источник: ros-industrial/robotiq, ветка kinetic-devel
#    Соответствие имён (наш URDF -> ros-industrial):
#      base -> base_link,  driver -> outer_knuckle,  coupler -> outer_finger,
#      follower -> inner_finger,  spring_link -> inner_knuckle,  pad -> pad

# 3. Перевести геометрию в .obj — конвертер Isaac Sim падает на .dae от Robotiq
python -c "import trimesh; [trimesh.load(f, force='mesh', process=False).export(f[:-4]+'.obj') for f in glob.glob('meshes/robotiq-2f/*/*.dae')]"

# 4. Абсолютные пути к мешам + инерция основанию (у panda_link0 её нет в URDF)

# 5. Импорт
python omnigibson/examples/robots/import_custom_robot.py --config droid_import.yaml
```

## Три причины, по которым импорт падает (все встречены и устранены)

| симптом | причина | лечение |
|---|---|---|
| `ValueError: string is not a file: .../link0.dae` | относительные пути к мешам | абсолютные пути |
| `No mass specified for link panda_link0`, затем segfault | у основания нет `<inertial>` — вырожденное тело | добавить массу и тензор инерции |
| segfault внутри `isaacsim.asset.importer.urdf` | конвертер не переваривает `.dae` от Robotiq | перевести геометрию в `.obj` |

Штатный аудит (`urdf_audit`) показывает первые две: поля `broken_relative_paths` и
`links_without_inertial`. Третья не диагностируется ничем — только падением.

## Результат

```
вращательных суставов 13, из них гриппера 6 — У ВСЕХ привод
   ведущие  robotiq_2f_85_{left,right}_driver_joint       0 .. 47.8 град
   колодки  robotiq_2f_85_{left,right}_follower_joint  -170 .. 170
   колена   robotiq_2f_85_{left,right}_spring_link_joint -170 .. 170
камера запястья gripper_link_camera на panda_link7 — поза перенесена из droid.usd
```

Управление гриппером сводится к таблице чисел в конфиге задачи
(`realm/config/robots/DROID2.yaml`), взятых из спецификации 2F-85, а не подобранных:

```
driver      (ведущий)  ход 0..0.834 рад,  множитель +1
spring_link (колено)                      множитель +1   -> вместе с ведущим
follower    (колодка)                     множитель -1   -> против ведущего
```

Зеркальность левой и правой половин в настоящем 2F-85 задана **посадочным разворотом на
180 град** (`rpy="0 0 3.14159"` у левой), а не противоположными знаками — множители у
обеих сторон одинаковые. Это тот факт, на подмене которого сломалась предыдущая
конструкция: в ремонтном ассете левая и правая половины получили разные посадочные
повороты (отличающиеся примерно на 90 град), из-за чего губки вставали под прямым углом.

## Что в собранной модели пришлось проверить отдельно

Сборка робота из URDF — это несколько десятков чисел, и часть из них импортёр не берёт
ниоткуда: их подставляет тот, кто собирает. Проверка 10.08.2026 прошла по всем таким
местам и нашла три ошибки из пяти. Ниже — чем каждое подтверждено, чтобы не проверять
заново по памяти.

| место | как проверено | итог |
|---|---|---|
| знаки в `closed_qpos` | `physics:localRot0` суставов: у левой половины (≈0,0,0,1) — разворот 180°, у правой (1,0,0,0), оси у всех X | одинаковые знаки верны |
| единицы углов | пределы ведущего сустава в USD: `0 .. 47.78` при `0 .. 0.834` в URDF | импортёр перевёл в **градусы** |
| пары без столкновений | у эталона 23 пары, у собранного — ни одной | перенесены 24 пары |
| поза камеры запястья | сравнение с `droid.usd` относительно `panda_link7` | была смещена, исправлена |
| масса основания | эталон объявляет 0.62977, было вписано 2.92 «по мотивам» franka_description | приведено к эталону |

### Камера запястья: смещение, взятое не с того уровня

В URDF камеры нет вообще, поэтому её добавляли вручную. Из `droid.usd` было взято
смещение `(-0.031, 0.074, -0.011)` и поворот на −18° — числа верные, но относятся
к **prim'у `Camera` внутри тела** `gripper_link_camera`, тогда как само тело закреплено на
`panda_link8` практически без сдвига. Подставленные в сустав, они увели камеру на 12 см и
довернули на лишние 18°.

Диагностика этой ошибки поучительна сама по себе: в самой модели ничего не ломается —
сцена грузится, картинка снимается, прогон идёт до конца. Видно только по числам, и
только если сравнивать с эталоном.

Правка вынесена в `attach_wrist_camera.py`: скрипт читает позу камеры из `droid.usd`
относительно `panda_link7` и воспроизводит её в собранной модели, вместе со смещением
сенсора внутри тела. Родителем выбран `panda_link7`, потому что `panda_link8` в URDF нет.
Проверка после переноса — расхождение 0.000000 м.

Оптику скрипт не трогает: OmniGibson ≥ 3.9.1 переписывает `focalLength` и
`horizontalAperture` значениями из конфига робота (`sensors/vision_sensor.py:260-263`),
поэтому действуют `focal_length: 2.8` / `horizontal_aperture: 5.376` из
`realm/config/robots/DROID2.yaml` — те же, что у эталона, то есть 87.7° по горизонтали.

### Что осталось как есть, хотя выглядит подозрительно

**Разные предельные усилия у половин гриппера**: `left_driver` 176 Н·м, `right_driver` 60.
Это не дефект сборки — так записано в самом `panda_robotiq_85.urdf`, из которого собран
и эталон. Воспроизводим авторский файл, а не исправляем его.

**Глубина посадки гриппера отличается от `droid.usd`**: в собранной модели база гриппера
на 0.045 м от `panda_link7`, в эталонном ассете — на 0.1225 м, и там между фланцем и
грипером стоит переходник (`gripper_link_coupling`), которого в URDF нет. То есть URDF и
USD у авторов описывают геометрически разные сборки одного робота. Сравнивать начала
координат звеньев напрямую нельзя — у моделей гриппера разные меши и разные точки
отсчёта, — поэтому вопрос закрывается только замером положения колодок в загруженной
сцене (`tests/gripper_repl.py`, команда `links`).

## Почему сборка отклонена

Замер геометрии загруженной модели (габариты визуальных и коллизионных мешей каждого
звена в системе этого звена, метры):

| звено | визуальный меш | коллизия |
|---|---|---|
| panda_link0 … panda_link7 | 0.11 … 0.23 | совпадает с визуальным ✔ |
| robotiq_2f_85_base | **7.50 × 8.48 × 9.40** | **75.2 × 86.2 × 94.2** |
| robotiq_2f_85_\*_driver | 2.40 × 4.63 × 2.29 | 0.024 × 0.046 × 0.023 ✔ |
| robotiq_2f_85_\*_coupler | 2.70 × 1.81 × 5.91 | 0.027 × 0.018 × 0.059 ✔ |
| robotiq_2f_85_\*_pad | 0.002 × 0.001 × 0.004 | 0.020 × 0.005 × 0.035 ✔ |
| robotiq_2f_85_**left**_follower | 1.50 × 2.99 × 5.05 | **нет** |
| robotiq_2f_85_**left**_spring_link | 3.90 × 4.91 × 5.54 | **нет** |

Рука собрана правильно. Гриппер — нет: база размером с дом, коллизия у неё же на порядок
крупнее визуала, у левой половины губок физического тела нет вовсе. Захват был невозможен
в принципе — независимо от знаков в конфиге, положения камеры и настроек контроллера.

Причина в исходных данных, а не в рецепте. В `panda_robotiq_85.urdf` меши подключены с
масштабами `scale="0.1"` (визуал) и `scale="0.001"` (коллизия) — то есть файл рассчитан на
геометрию в определённых единицах. Самой геометрии в репозитории REALM нет: подставлены
меши из `ros-industrial/robotiq`, у которых единицы другие и у визуала с коллизией разные.
Отсюда и разнобой.

Побочно это объясняет две вещи, на которые ушло время: пустой серый кадр с камеры
запястья (камера оказывалась внутри визуального меша базы размером 7.5 × 9.4 м) и
необходимость гасить два десятка пар столкновений вручную.

### Чем заменено

Стоковый `franka_robotiq` из BEHAVIOR-1K — та же связка Franka Panda + Robotiq 2F-85,
геометрия и коллизии выверены разработчиками, камера запястья стоит штатно как
`camera_link` на `panda_link7`. Замеры в загруженной сцене против эталонного `droid.usd`:

| | глубина губок под panda_link7 | камера под panda_link7 | ход губок |
|---|---|---|---|
| эталон `droid.usd` (baseline 0.61) | 0.234 | 0.1225 | — |
| **стоковый franka_robotiq** | **0.2275** | **0.1120** | 0.0997 → 0.0165 м |
| собранный `droid2` | 0.143 | 0.1225 | губки без коллизий |

Сток отличается от эталона на 0.7 см по глубине схвата и 1 см по камере; собранный робот —
на 9 см. Кадр с камеры запястья у стока совпадает с кадром прежних прогонов на эталонном
ассете: та же сцена, тот же угол, губки в том же месте кадра.

`realm/inference/utils.py` уже умеет находить камеру и под именем `camera_link` — это было
сделано раньше, когда обнаружилось, что при отсутствии ожидаемого ключа REALM молча
подставляет чёрный кадр.
